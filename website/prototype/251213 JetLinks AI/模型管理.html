应放在哪个模块 / 子菜单

主菜单：模型管理（Model Management）

推荐子菜单与结构（优先级从上到下）：

模型管理

├─ 预置模型（Base Models）

├─ 适配器管理 / 微调适配器（Adapters / LoRA） ← 推荐放这里

├─ 模型版本（Model Versions）

└─ 部署 / 服务（Deployments）

理由：LoRA 既不是完整模型也不是纯数据集，它与模型密切相关但需要单独的生命周期管理（版本、兼容性、合并）。放在模型管理下最直观，也便于和 base model 做映射、权限与部署关联。

三、适配器管理页面应包含的表格列与元数据（必备）

每一行对应一个 LoRA artifact（或适配器版本）：

名称（Name）

ID（内部唯一 id）

Base model（训练时使用的基础模型）

兼容性（框架/版本，例如：transformers 4.30 / HF model id）

版本号（v1.0）

训练任务/用途（classification / NER / dialogue）

训练数据集（名称/版本，或数据哈希）

Rank / LoRA 超参（r, alpha, dropout）

大小（MB）

创建者（user）

创建/更新日期

状态（Draft / Trained / Validated / Merged / Deprecated）

评分/验证结果（简单指标，如验证集 loss / task metric）

标签（tags：e.g. “推理安全已校验”, “适用于边缘部署”）

四、允许的操作（动作按钮）

在列表/详情页提供：

预览/查看元数据

上传/新建（Upload）

关联 Base Model（Bind） / 解除关联

加载到模型（Attach） — 在测试环境动态叠加

合并（Merge） — 把 LoRA 烧入 base 并生成“新完整模型”

验证/测试（Run Evaluation） — 触发单测或评估任务

下载（Download）

克隆 / 创建新版本（Clone / New version）

删除 / 弃用（Soft delete / Deprecate）

权限与共享（Share / ACL）

oRA 权重不能自动适配不同大模型，且必须严格绑定到其对应的基础模型（Base Model）。

你不允许在边端“自动匹配多个不同大模型”或“通用加载”。

原因如下：

LoRA 训练结果依赖 基础模型的特定参数名、层结构、维度、Tokenizer。

不同大模型（即便同系列不同大小）结构也不一致。

LoRA 权重是针对某个基础模型的“差分权重”，对其它模型加载会直接报错或输出异常。

因此边端必须加载：

LoRA 权重 + 对应的基础模型版本（完全一致）。

LoRA 权重下发后，是否自动加载取决于你们平台的“边端推理运行时（Edge Runtime）”的设计。

常见设计 A：默认自动加载（云边 AI 平台常用）

流程如下：

云端下发 LoRA → 边端收到 LoRA 文件

边端读取 LoRA metadata

检查对应大模型是否存在

存在 → 自动加载

不存在 → 自动下载基础模型 → 再加载

这种模式适合 IoT 运维：减少手工操作。

PRD 可写一句：

“边端在收到新的 LoRA 权重后会按 metadata 自动完成基础模型检查与加载。”

部署触发：从模型管理直接触发部署（云端或下发边缘），部署前必须进行兼容性校验（模型大小、框架版本、quantization 支持、依赖库）。
