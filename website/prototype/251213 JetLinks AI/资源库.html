#### 3.2.2 页面二：新建/编辑部署向导 (The Wizard - 核心流程)

**设计理念：** 分步引导，将复杂的配置（如转换参数）折叠，突出核心业务逻辑（挂载 LoRA）。


**Step 1: 基础环境配置**

*   **服务名称**：输入框。

*   **部署目标**：

    *   单选框：`云端推理` / `边缘设备`。

    *   **设备选择器**：若选边缘设备，弹出设备树（支持按标签筛选“算能设备”）。系统需自动校验设备在线状态及剩余算力。


**Step 2: 模型配置 (核心交互点)**

*   **选择基础模型**：下拉框选择系统预置的大模型（如 Qwen2-7B-Instruct）。

*   **高级微调配置 (LoRA 挂载)**：

    *   **UI形态**：一个清晰的 `Switch` 开关 —— **[ ] 启用 LoRA 微调权重**。

    *   **交互动作**：开启后，下方展开**“权重文件选择器”**面板。

    *   **数据源**：调用「模型管理」模块的 API，展示用户训练好的 LoRA 列表。

    *   **选择逻辑**：

        *   列表显示：`任务名称` | `训练时间` | `Loss值` | `备注`。

        *   **版本控制**：选中某个任务后，需进一步选择具体的 `Checkpoint` (例如：Epoch-10, Step-500)。

        *   *设计亮点*：提供一个**“效果对比”**的超链接，点击可弹窗查看该 LoRA 在训练时的评估报告，辅助用户决策。


未找到适配该设备芯片架构的模型文件

这是一个非常经典的**多架构（Heterogeneous）边缘分发**问题。


简单回答你的第一个问题：**是的，必须生成多个独立的文件。**

因为不同芯片的底层指令集完全不同（例如算能是 TPU 指令，英伟达是 CUDA 指令），它们的文件结构、二进制编码甚至文件后缀（.bmodel vs .engine vs .rknn）都是风马牛不相及的。


为了实现**“用户操作一次，所有不同芯片的网关都能收到正确文件”**，你需要在系统设计中引入**“逻辑版本（Logical Version）”**与**“物理制品（Physical Artifact）”**分离的概念。


这里是详细的设计方案：


---


### 核心设计理念：类似于 "App Store"

这就好比你在 App Store 发布微信。你只需要发布“微信 v8.0”，但实际上后台有“iOS版”和“Android版”两个包。用户点击下载时，商店会自动根据用户的手机型号下发正确的那个包。


### 1. 数据结构设计


你需要构建一个**“发布包 (Release Bundle)”**的概念，而不是直接下发单一文件。


#### A. 资产/模型表 (Model_Version)

这是用户眼中的“一个东西”。

| Version ID | 名称 | 描述 | 状态 |

| :--- | :--- | :--- | :--- |

| V1001 | 医疗问答LoRA_v1.0 | 包含5个网关的3种格式 | 已转换完成 |


#### B. 制品/文件表 (Artifacts)

这是实际存在的物理文件。

| Artifact ID | 所属 Version ID | 芯片架构 (Tag) | 文件路径 | 文件哈希 (MD5) |

| :--- | :--- | :--- | :--- | :--- |

| A_01 | V1001 | `sophgo_bm1684x` | `/s3/lora_v1_sophgo.bmodel` | a1b2... |

| A_02 | V1001 | `nvidia_orin` | `/s3/lora_v1_nvidia.engine` | c3d4... |

| A_03 | V1001 | `rockchip_3588` | `/s3/lora_v1_rk.rknn` | e5f6... |


#### C. 设备注册表 (Device_Registry)

你需要知道每个网关是什么芯片。

| Device ID | 芯片架构 | 在线状态 |

| :--- | :--- | :--- |

| GW_01 | `sophgo_bm1684x` | Online |

| GW_02 | `sophgo_bm1684x` | Online |

| GW_03 | `nvidia_orin` | Online |

| ... | ... | ... |


---


### 2. 流程设计：如何实现“一次性下发”


**用户视角：**

1.  点击“智能转换”。系统提示：“检测到 3 种架构，生成了 3 个文件”。

2.  点击“**批量下发**”。

3.  进度条走完，提示“5 台设备下发成功”。


**系统后台视角（关键逻辑）：**


#### 第一步：打包与映射 (Packaging)

当“智能转换”完成后，不要把 3 个文件当作散乱的文件，而是创建一个**“分发任务单”**。

系统记录：`Task_X = { Target: "All Gateways", Content: "LoRA_v1.0 (Logical)" }`


#### 第二步：任务拆解 (Task Splitting)

当下发指令发出时，分发服务（Dispatcher）遍历所有目标网关，进行**动态路由**：


*   **遍历 GW_01 (算能):**

    *   查询网关芯片类型 -> `sophgo_bm1684x`

    *   在 V1001 制品表中查找 tag 为 `sophgo_bm1684x` 的文件 -> 找到 `A_01`

    *   **生成子任务：** 向 GW_01 推送 `lora_v1_sophgo.bmodel`


*   **遍历 GW_03 (英伟达):**

    *   查询网关芯片类型 -> `nvidia_orin`

    *   在 V1001 制品表中查找 tag 为 `nvidia_orin` 的文件 -> 找到 `A_02`

    *   **生成子任务：** 向 GW_03 推送 `lora_v1_nvidia.engine`


#### 第三步：并行传输

系统并行执行上述子任务。


---


### 3. 工具提示文案建议


针对这种设计，你的“批量下发”按钮的工具提示可以这样写，给用户一种“智能、省心”的感觉：


**场景：用户点击“下发”按钮时**


> **“智能分发模式：系统将根据每台边缘网关的芯片类型（如算能、英伟达等），自动从转换包中匹配并下发对应的格式文件。无需手动筛选设备。”**


### 4. 异常处理设计（Tips）


在设计时要注意一个边缘情况：**如果不匹配怎么办？**


假如你有一个新的边缘网关是“华为昇腾”芯片，但你只转换了“算能”和“英伟达”的格式。

*   **转换时：** “智能转换”应该扫描全网，发现有华为芯片，提示用户“是否也要转换为华为格式？”（如果你的转换引擎支持的话）。

*   **下发时：** 如果制品表中找不到对应芯片的文件，该网关的子任务应报错：**“下发跳过：未找到适配该设备芯片架构的模型文件。”**


### 总结

1.  **文件层面：** 是多个文件。

2.  **管理层面：** 是一个“版本包”。

3.  **下发层面：** 是“动态路由”，系统自动做 `Device Type -> File Format` 的连线题。
